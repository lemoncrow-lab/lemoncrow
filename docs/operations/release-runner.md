# LemonCrow release runner

The `Release qualification` workflow uses `[self-hosted, linux, lemoncrow-release]`. **One local organization-level runner** (`lemoncrow-local` on `pankaj-rog`) has both `lemoncrow-release` and `desktop-fallback-lemoncrow` labels. It replaces the separate repo-level release and org-level fallback registrations. Do not register a second LemonCrow runner. The restricted `desktop-fallback-private` group permits trusted `main` fallback/release workflows; the exact protected `v0.8.2` tag has also been allowlisted. Future release tags need their own exact-ref allowlisting. The tag path uses Git-impact selection; scheduled/manual `main` uses the bounded confidence profile, not the former exhaustive suite.

## Active local installation (one runner)

The operator chose the existing 32-core desktop rather than a paid VM. This is **not VM isolation**: the nested Docker daemon (`lemoncrow-release-dind`) is a privileged container, but has no host Docker socket, home-directory mounts, or published ports. The unprivileged runner (`lemoncrow-runner`) shares the nested daemon's network namespace (inside the `lemoncrow-release-isolated` Docker network), allowing the release gate's loopback-only PostgreSQL and Redis ports to be reached without mounting the host Docker socket. Both containers are bound to the **same four distinct physical performance cores (logical CPUs 0, 2, 4, 6; not four efficiency cores)** with a four-core cgroup quota / 32 GiB RAM and restart automatically. The running runner image was created before the Dockerfile switched its default worker environment from 12 to 4: the GitHub release workflow explicitly sets `LEMONCROW_TEST_WORKERS=4`; image defaults take effect after a guarded runner replacement. Only one GitHub organization runner registration exists; the nested Docker daemon is infrastructure, **not another GitHub runner**.

Inspect: `docker ps --filter name=lemoncrow-`, `docker logs --tail 40 lemoncrow-runner`, `gh api orgs/lemoncrow-lab/actions/runners --jq '.runners[]|{name,status,labels:[.labels[].name]}'`. A fresh installation on this machine is provided by `bash scripts/install_local_release_runner.sh --install`, which refuses to overwrite an existing registration or container. Never mount `/var/run/docker.sock` or GitHub/SSH secrets into the runner. Do not grant public repositories or PR workflows access to the `desktop-fallback-private` runner group. The historical dedicated-VM alternative is below for future improved isolation.

**Sandbox policy:** The runner keeps `--cap-drop ALL`, `no-new-privileges`, four pinned CPUs, no host mounts and no host Docker socket. Its pinned `deploy/local-release-runner/seccomp.json` is derived from Moby's default seccomp profile (upstream SHA256 `6416b47770785a41ac59073cdc77d9fe98517df2799dc83ef207e622de3053f6`) with only namespace/mount-related syscalls additionally permitted; `clone3`'s default ENOSYS override was removed. Ubuntu AppArmor still prevents user-namespace mounts with the standard Docker profile, so the runner container uses `apparmor=unconfined`. The full worker also requires a fresh `/proc` mount, blocked by Docker's default masked system paths even when simple user namespaces succeed; the runner therefore uses `systempaths=unconfined`. **These relax two Docker security layers** but not Linux capabilities or `no-new-privileges`. The runner must never handle PR/fork jobs. Accept only protected `main` and exact allowlisted release-tag jobs, never PRs or public repositories; prefer a dedicated four-core VM for stronger kernel isolation. A disposable 4-core/no-network/no-capabilities/no-new-privileges container passed real `bwrap --unshare-all --ro-bind / / true` with the pinned policy. Install-time preflight now refuses to register a runner when that probe fails.

**Security and qualification limits:** Host/guest kernel is shared, so privileged DinD carries more risk than a dedicated VM; run only trusted `main` jobs and protected releases. Concurrent desktop workloads can invalidate G9 performance timings—do not relax SLO targets in response. The former pin to efficiency cores 16–19 (4.4 GHz maximum) was incompatible with release latency targets; a four-logical-CPU comparison on performance cores 0,2,4,6 (5.7 GHz maximum) passed all three Python release SLOs without raising limits (capture_small 567.8/620 ms, incremental_delta 338.7/430 ms, brief_projection 81.0/180 ms p95). This targeted measurement is not a full passing G11. The `release-qualification` GitHub environment permits `main` and `v*` tags, but the runner group requires exact workflow/ref allowlisting: `v0.8.2` was allowlisted on November 2, and future signed release tags must be explicitly allowlisted by exact ref. GitHub does not accept `@refs/tags/v*` as a workflow-group selection. The earlier tagged four-core GitHub job passed its CPU assertion but stopped at the private `landing` marketing-site checkout: `LEMONCROW_RELEASE_LANDING_READ_KEY` was absent. That step is now removed because `infra.clean_checkout` intentionally leaves marketing submodules uninitialized and the passing 49-component local report was produced from that exact checkout mode. The release still tests **product Review landing**, signature and authority semantics; it does **not** test the independent private marketing website. No deploy key or personal PAT is necessary. The previous runner image could not create the real worker's Bubblewrap `/proc` and `/dev` mounts, producing root-confidence and hosted-worker failures; a simple namespace-only probe was insufficient. The rebuilt runner enables user namespaces plus fresh process/device mounts without Linux capabilities. Its full mount-contract preflight now rejects unsupported kernels before expensive qualification. These earlier failures were unreleasable, never safe skips. The four-core candidate-upgrade probe also exposed a missing `ps` executable in the runner image: the local server's process supervisor uses `ps` to stop the previous installation before starting the upgraded one. `procps` is now an explicit runner-image and release preflight dependency, not an optional installer tool. A temporary manual addition of `ps` to the previous container proved the cause: with `LEMONCROW_INSTALL_RTK=0`, the same prebuilt `v0.8.2` candidate passed the four-core upgrade in 49 seconds and the compiled-client/Review slice in 33 seconds. `procps` and `libxkbcommon0` are now installed in the reproducible runner image; the latter is required by Playwright Chromium. These are partial checks, **not** a full 49-component, four-core release qualification. The full workflow no longer requires stochastic Workspaces Lite cost evidence. The independent `runtime-credit` diagnostic still requires exact-commit, provider-reported paired manifests stored as protected environment secrets and fails if missing or over its original 10% cost / 15% fresh-input bounds. A separate post-gate verification checks the **actual report's** four-core affinity, four-core cgroup quota, pinned performance-core CPUs 0,2,4,6 and <=55-minute execution time; a timing simulation alone cannot satisfy it.

## Optional dedicated VM setup

For a stronger future security boundary, use a dedicated Ubuntu x86-64 VM with 16 vCPU, 32 GiB RAM, and 200+ GiB of disk; avoid shared development/staging hosts. The VM setup below registers a *repo-level* runner and **must not be used while the current unified organization runner is registered**. Retire the active runner first to maintain one LemonCrow runner.

## On the clean release VM

1. Install and start Docker Engine. Add only the runner service user to the local `docker` group, making this safe only because the VM is dedicated. Prepare Node.js/npm, Git, Python 3, uv, bubblewrap, Helm, kubectl, Terraform and systemd. Configure noninteractive `sudo` for the VM's runner user before the one-time service installation, and protect access to that user as a privileged operator on this dedicated VM. The release gate itself provisions fresh PostgreSQL 17 and Redis via Docker, installs managed Python dependencies via uv and runs Playwright's browser bootstrap. Ensure system-wide sandbox tool paths include Helm/kubectl/Terraform; see `scripts/release_gate.py`'s `SANDBOX_PATH`.
2. Clone `lemoncrow-dev` into the release VM, and run `bash scripts/register_release_runner.sh --check` as its non-root service user. **Do not log in to GitHub CLI on the runner**; an administrator token left on disk would be accessible to jobs. On a *separate operator workstation* with repository admin rights, mint a short-lived token with `gh api repos/lemoncrow-lab/lemoncrow-dev/actions/runners/registration-token -X POST --jq '.token'`. Do not save or log it.
3. Supply the token through secure stdin to `bash scripts/register_release_runner.sh --install` on the release VM (the script also prompts without echoing when used interactively). For example, from the operator workstation: `token="$(gh api repos/lemoncrow-lab/lemoncrow-dev/actions/runners/registration-token -X POST --jq '.token')"; printf '%s\n' "$token" | ssh release-user@dedicated-vm 'cd lemoncrow-dev && bash scripts/register_release_runner.sh --install'; unset token`. The installer SHA256-verifies the pinned official GitHub Actions runner archive, configures the repository runner and installs its systemd service. No release qualification is launched automatically.
4. On the operator workstation, verify that GitHub shows the runner `online` using `gh api repos/lemoncrow-lab/lemoncrow-dev/actions/runners --jq '.runners[] | {name,status,busy,labels}'`. Confirm `release-qualification` environment branch/tag restrictions and the required read-only landing-submodule deploy key before the first release job. Inspect a light/no-op job before executing any multi-hour gate.

All release reports remain on the runner for the duration of the job and are uploaded only through the protected workflow. The release gate uses fresh checkouts/services and refuses dirty or incomplete evidence. Reprovision the VM after any compromise; do not reuse it for normal development.

## Qualification reduction policy

The release-critical profile contains 46 components, with seven root, eight enterprise, five client and four public-server test files; eight browser E2E specs; runtime-credit correctness tests; and selected high-risk Gate G/K rows. Hosted-load fairness, G9 p95 and priced provider-credit evidence remain independently runnable diagnostics (49-component extended catalog), not release-stamping gates because shared-host performance and short stochastic provider samples are nondeterministic. Full 12k+/5k+ regression suites, 50k-file scale and repeated-sample Gate H measurements remain separate developer/diagnostic checks. The local `v0.8.2` report passed in 30.48 minutes on a 32-logical-CPU desktop with three component slots: it is **not** proof of the four-core 60-minute objective. The actual four-core runner must pass every selected security/upgrade test and produce its own clean release report. Do not treat an abbreviated or skipped run as releasable.

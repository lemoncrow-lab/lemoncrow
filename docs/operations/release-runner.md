# LemonCrow release runner

The `Release qualification` workflow uses `[self-hosted, linux, lemoncrow-release]`. As of November 1, 2026 **one local organization-level runner** (`lemoncrow-local` on `pankaj-rog`) has **both** `lemoncrow-release` and `desktop-fallback-lemoncrow` labels. It replaces the former separate repo-level release runner and older org-level fallback runner; do not register two LemonCrow runners. The `desktop-fallback-private` runner group permits the LemonCrow `main` release workflow plus the existing LemonCrow/landing fallback workflows. The CI tag path uses Git-impact selection; scheduled and manually dispatched `main` remain exhaustive.

## Active local installation (one runner)

The operator chose the existing 32-core desktop rather than a paid VM. This is **not VM isolation**: the nested Docker daemon (`lemoncrow-release-dind`) is a privileged container, but has no host Docker socket, home-directory mounts, or published ports. The unprivileged runner (`lemoncrow-runner`) shares the nested daemon's network namespace (inside the `lemoncrow-release-isolated` Docker network), allowing the release gate's loopback-only PostgreSQL and Redis ports to be reached without mounting the host Docker socket. Both containers are limited to 12 vCPUs / 32 GiB RAM and restart automatically. Only one GitHub organization runner registration exists; the nested Docker daemon is infrastructure, **not another GitHub runner**.

Inspect: `docker ps --filter name=lemoncrow-`, `docker logs --tail 40 lemoncrow-runner`, `gh api orgs/lemoncrow-lab/actions/runners --jq '.runners[]|{name,status,labels:[.labels[].name]}'`. A fresh installation on this machine is provided by `bash scripts/install_local_release_runner.sh --install`, which refuses to overwrite an existing registration or container. Never mount `/var/run/docker.sock` or GitHub/SSH secrets into the runner. Do not grant public repositories or PR workflows access to the `desktop-fallback-private` runner group. The historical dedicated-VM alternative is below for future improved isolation.

**Security and qualification limits:** Host/guest kernel is shared, so privileged DinD carries more risk than a dedicated VM; run only trusted `main` jobs and protected releases. Concurrent desktop workloads can invalidate G9 performance timings—do not relax SLO targets in response. The `release-qualification` GitHub environment permits `main` and `v*` tags, but the *runner group* currently permits the release workflow only on `main`: a new signed release tag must be explicitly allowlisted by exact ref before a tagged job can use this runner. GitHub does not accept `@refs/tags/v*` as a workflow-group selection. The private `landing` submodule still needs a read-only credential configured in the protected environment (deploy keys are currently disabled by the organization); this is separate from runner availability.

## Optional dedicated VM setup

For a stronger future security boundary, use a dedicated Ubuntu x86-64 VM with 16 vCPU, 32 GiB RAM, and 200+ GiB of disk; avoid shared development/staging hosts. The VM setup below registers a *repo-level* runner and **must not be used while the current unified organization runner is registered**. Retire the active runner first to maintain one LemonCrow runner.

## On the clean release VM

1. Install and start Docker Engine. Add only the runner service user to the local `docker` group, making this safe only because the VM is dedicated. Prepare Node.js/npm, Git, Python 3, uv, bubblewrap, Helm, kubectl, Terraform and systemd. Configure noninteractive `sudo` for the VM's runner user before the one-time service installation, and protect access to that user as a privileged operator on this dedicated VM. The release gate itself provisions fresh PostgreSQL 17 and Redis via Docker, installs managed Python dependencies via uv and runs Playwright's browser bootstrap. Ensure system-wide sandbox tool paths include Helm/kubectl/Terraform; see `scripts/release_gate.py`'s `SANDBOX_PATH`.
2. Clone `lemoncrow-dev` into the release VM, and run `bash scripts/register_release_runner.sh --check` as its non-root service user. **Do not log in to GitHub CLI on the runner**; an administrator token left on disk would be accessible to jobs. On a *separate operator workstation* with repository admin rights, mint a short-lived token with `gh api repos/lemoncrow-lab/lemoncrow-dev/actions/runners/registration-token -X POST --jq '.token'`. Do not save or log it.
3. Supply the token through secure stdin to `bash scripts/register_release_runner.sh --install` on the release VM (the script also prompts without echoing when used interactively). For example, from the operator workstation: `token="$(gh api repos/lemoncrow-lab/lemoncrow-dev/actions/runners/registration-token -X POST --jq '.token')"; printf '%s\n' "$token" | ssh release-user@dedicated-vm 'cd lemoncrow-dev && bash scripts/register_release_runner.sh --install'; unset token`. The installer SHA256-verifies the pinned official GitHub Actions runner archive, configures the repository runner and installs its systemd service. No release qualification is launched automatically.
4. On the operator workstation, verify that GitHub shows the runner `online` using `gh api repos/lemoncrow-lab/lemoncrow-dev/actions/runners --jq '.runners[] | {name,status,busy,labels}'`. Confirm `release-qualification` environment branch/tag restrictions and the required read-only landing-submodule deploy key before the first release job. Inspect a light/no-op job before executing any multi-hour gate.

All release reports remain on the runner for the duration of the job and are uploaded only through the protected workflow. The release gate uses fresh checkouts/services and refuses dirty or incomplete evidence. Reprovision the VM after any compromise; do not reuse it for normal development.

## Qualification reduction policy

The always-required G1 status, G8 secret/canary and signed-record gates already execute 280 Python cases which the root suite repeated in the October 27 run; release-only root deduplication omits the second execution, never the gate proof. The release browser profile is an explicit 13-spec core that retains capture, navigation, edits, feedback, failure/rollback, snapshot races, finish, previews, accessibility and mobile checks. The exhaustive developer browser profile remains `make review-e2e`. Impact-selected test-file edits can still exercise non-core specifications, and scheduled full runs still exercise the root/enterprise suites with real gate coverage. Performance SLOs, privilege isolation, data integrity, PostgreSQL migrations/restore, signatures, real SCM canary and the compiled installer are **not** removed. A reduction is not proof of equivalent defect detection without subsequent green release evidence.
